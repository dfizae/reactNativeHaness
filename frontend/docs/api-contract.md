# <프로젝트 이름> API 계약 사본

> 템플릿이다. `<…>` 를 프로젝트 값으로 채운다. 백엔드가 OpenAPI 를 내보내면 `openapi/openapi.yaml` 로 옮기고 이 파일은 삭제한다(규칙 90).
>
> **원천**: <팀 API 명세서·ERD 의 위치와 대조한 일시>. 백엔드가 OpenAPI 를 내보내기 전까지 이 파일이 `.agents/rules/90-backend-contract.md` 가 말하는 "클라이언트 쪽 계약 사본"이다.
> 아래 응답 형태가 명세일 뿐 실제 서버 응답이 아닌 동안에는, 구현 후 다르면 클라이언트에서 우회하지 말고 불일치를 보고한다.
> **상세 미확인** 은 명세의 상세를 아직 읽지 않은 항목, **URL 미확인** 은 경로가 비어 있는 항목에 붙인다.

## 1. 공통 규약

규칙 80·90 과 `docs/api-guide.md` 가 "계약을 따른다"고 한 값은 모두 이 표가 기준이다. 비워 두지 않는다.

| 항목 | 값 | 출처 |
| --- | --- | --- |
| Base path | <예: `/api/v1`> (호스트는 `EXPO_PUBLIC_API_URL`) | |
| 인증 | <헤더 형식, 토큰 수명, 인증이 필요 없는 엔드포인트> | |
| 토큰 갱신 | <갱신 엔드포인트와 요청·응답 형태> | |
| 성공 응답 | <공통 봉투가 있으면 형태와 데이터 위치, 없으면 "본문이 데이터". 빈 본문 성공의 형태> | |
| 오류 응답 | <형태(`code`·`message`·추적 id), `message` 를 사용자에게 그대로 보여도 되는지, 공통 HTTP 상태의 뜻> | |
| 명명 | <camelCase / snake_case, path·query·body 사용 규칙> | |
| 금액 | <원 단위 정수 JSON number / 문자열 직렬화 등> | |
| 날짜·시각 | <형식과 시간대 표기 여부> | |
| 페이지네이션 | <방식, 요청 파라미터, 응답 형태, 마지막 페이지 표시> | |
| 멱등성 | <멱등성 키 헤더 유무, 없으면 서버가 중복을 막는 방법> | |
| 시간대 | <서버 시간대, 오프셋 없는 값의 해석> | |

우선순위 P0 = MVP. 배포 여부가 표와 다르면 날짜와 함께 표 위에 적는다.

| 도메인 | Use Case | Method | URL | P | 담당 |

## 3-0. 오류 코드 카탈로그

확인된 코드만 적는다. 여기 없는 `code` 를 어떻게 보여줄지는 §1 오류 응답을 따른다.

| code | HTTP | 뜻 |
| --- | --- | --- |
| <`AUTH_001`> | <401> | <로그인 실패> |

## 3. 엔드포인트 상세

타입은 TypeScript 표기. `?` 는 선택(응답에서는 조건부로 오거나 `null`). 열거형 값은 §4. 도메인마다 절을 만들고, 엔드포인트마다 메서드·경로·성공 상태, 요청·응답 타입, 오류 코드를 적는다.

### <도메인>

```ts
// <확인 일시와 근거(명세·Swagger·코드)>

// POST /auth/login — 200
type LoginRequest = { email: string; password: string };
type LoginResponse = { accessToken: string; refreshToken: string };
// 401 AUTH_001 로그인 실패
```

## 6. 이 문서를 갱신하는 법

1. 원천(<명세 위치>)에서 바뀐 항목을 읽는다.
2. §2 표와 §3 타입을 고치고 머리말의 기준 일시를 갱신한다.
3. 바뀐 필드를 쓰는 `features/<domain>/model.ts` 와 `api/mocks/` 를 함께 고친다.
