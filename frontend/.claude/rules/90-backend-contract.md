# 백엔드 API 계약

이 규칙은 백엔드 계약을 소비하는 클라이언트 코드에 적용한다. 프로젝트마다 달라지는 값(Base path, 응답 봉투, 명명, 금액·날짜 형식, 인증 헤더와 토큰 수명, 페이지네이션, 멱등성, 오류 코드)은 이 규칙에 적지 않고 `docs/api-contract.md` §1 공통 규약에 적는다. 이 규칙은 그 값을 코드에서 어떻게 다루는지만 정한다. 두 문서가 다르면 계약 사본이 우선하고 이 규칙을 고친다.

## 계약 원천

- 계약의 원천(백엔드의 OpenAPI 스펙, 팀 API 명세서·ERD 등)은 프로젝트가 정하고 `docs/api-contract.md` 머리말에 적는다. OpenAPI 가 나오기 전까지 클라이언트 쪽 계약 사본은 `docs/api-contract.md`(원천 대조 일시 명시)다. OpenAPI 스펙이 제공되면 `openapi/openapi.yaml`(또는 `.json`)로 복사본을 두고 버전(`info.version`)과 출처 커밋을 `openapi/README.md`에 기록한 뒤 `docs/api-contract.md` 는 삭제한다.
- `api/generated/`는 스펙에서 생성한 타입·클라이언트 코드다. 직접 수정하지 않고 `pnpm api:generate`로 재생성한다. 생성 도구(`openapi-typescript` 등)의 도입은 승인 후 진행한다.
- 스펙에 없는 엔드포인트, 필드, 상태값을 클라이언트에서 임의로 가정하지 않는다. 필요한 변경은 백엔드에 요청하고 보고서에 `TBD`로 남긴다.
- 스펙과 실제 응답이 다르면 클라이언트에서 우회하지 않고 불일치를 보고한다.

## DTO와 화면 모델

- 요청 DTO, 응답 DTO는 계약 사본(또는 생성된 타입)을 그대로 쓰고, 화면에서 쓰는 모델은 `features/<domain>/model.ts`에서 변환한다. 화면 컴포넌트가 DTO 필드명에 직접 의존하지 않게 한다.
- 명명(`camelCase`·`snake_case`)은 계약을 따르며 클라이언트에서 임의로 변환 레이어를 두지 않는다. 변환이 필요하면 `api/client.ts` 인터셉터 한 곳에서 한다.
- 응답이 공통 봉투(예: `{ success, code, message, data }`)로 오는 계약이면 봉투를 벗기는 일은 `api/envelope.ts` 의 `unwrapEnvelope`(응답 인터셉터에서 호출)만 하고, 도메인 함수와 `model.ts` 는 봉투를 모른다. 빈 본문 성공(`data: null`)은 `void` 로 다룬다. 목 데이터는 인터셉터를 거치지 않으므로 `api/mocks` 에는 봉투를 두지 않는다.
- 금액 필드의 직렬화 형식은 계약을 따른다. `model.ts` 에서 형식을 검증한 뒤(정수 JSON number 면 `Number.isSafeInteger`) `lib/money.ts` 의 `KRW`(문자열)로 바꿔 화면에 넘긴다. 잔액·잔여율·부족액 같은 서버 파생값은 검증만 하고 클라이언트에서 다시 계산하지 않는다.
- 날짜·시각은 계약의 형식을 그대로 받고 화면 모델 변환 시점에만 파싱한다. 시간대가 없는 값이면 계약이 정한 시간대를 붙여 파싱한다.
- 열거형(거래 상태, 계좌 종류 등)은 스펙의 값을 유니온 타입으로 두고, 스펙에 없는 값이 오면 `UNKNOWN`으로 흡수해 화면이 깨지지 않게 한다.

## 오류 응답

- 오류 응답의 형태(봉투 여부, `code`·`message`, 추적 id 유무)는 계약을 따른다. `toApiError` 가 `ApiError` 로 정규화하고, 다른 형태가 오면 계약 불일치로 보고한다.
- `code`는 화면 분기에 사용한다. 사용자 문구는 `features/<domain>/errors.ts`에서 `code`별로 정의한다. 정의가 없는 `code` 에 서버 `message` 를 폴백으로 보여줄지는 계약(서버 `message` 가 사용자 문구인지)을 따른다. `message` 를 파싱해 분기하지 않는다.
- HTTP 401은 계약의 갱신 엔드포인트로 토큰을 갱신한 뒤 1회 재시도하고, 갱신 실패 시 토큰을 지우고 로그인으로 이동한다. 갱신은 단일 실행(동시 401 은 같은 Promise 를 기다린다). 403은 재시도하지 않는다. 409는 계약 사본의 뜻대로 문구를 보여준다.

## 인증 헤더와 공통 규약

- 공통 헤더(`Authorization: Bearer <accessToken>` 등 계약이 정한 것)는 `api/client.ts` 인터셉터에서만 붙인다. 인증이 필요 없는 엔드포인트(가입·로그인·토큰 갱신)는 제외한다. 개별 API 함수에서 헤더를 조립하지 않는다.
- 돈이 움직이는 요청의 중복 실행을 막는 방식은 계약을 따른다(규칙 80). 클라이언트는 `isPending` 동안 같은 요청을 다시 보내지 않는다.
- 페이지네이션은 계약의 방식을 따른다. 커서 방식이면 `cursor`·`size`·응답 `nextCursor`(마지막 페이지는 `null`)를 TanStack Query `useInfiniteQuery`와 연결한다.
- 요청 타임아웃은 조회 10초, 돈이 움직이는 요청 30초를 기본으로 하되 `api/client.ts`에 상수로 둔다.
- 서버 시각·기기 시각 차이가 큰 경우를 대비해 응답 헤더 `Date`로 오프셋을 보정하는 로직은 `lib/date.ts`에 둔다.

## 목 서버와 테스트

- 백엔드가 준비되지 않은 엔드포인트는 도메인 함수의 목 분기(`EXPO_PUBLIC_API_URL` 이 비면 켜짐, `docs/api-guide.md` §9)로 대체하고, 목 데이터는 `api/mocks/`에 계약 사본의 응답 예시를 그대로 옮겨 두며 실제 계좌·개인 정보를 넣지 않는다. `msw` 등 목 서버 도입은 승인 후 진행한다.
- API 함수·모델 테스트는 계약 사본의 예시 응답을 기준으로 작성하고, 오류 응답, `null` 필드, 페이지네이션 경계(`nextCursor: null`)를 포함한다.
